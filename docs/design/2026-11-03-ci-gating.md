# Required CI checks for the exact head: design proposal

- Date: 2026-11-03
- Status: proposal, revision 2. Not implemented. Hostile review round 1 (CI-01
  to CI-04 and notes) is resolved in [Review resolution](#review-resolution).
  Issue [#17](https://github.com/nkovanen/agent-contrib/issues/17), the gating
  half. The report-only `verify --observe-ci` already ships in the v0.3.0
  candidate.
- Base: `efe7e68` (unreleased v0.3.0 candidate).
- Decision taken: the field extends the unreleased task schema 0.2 (no 0.3).

## Summary

Evidence is self-attested. Once the draft PR exists, GitHub can report CI
results for its exact head, as an observation the worker did not write. This
design proposes one opt-in gate with the simplest rule that fails closed on any
ambiguity.

1. **Declaration.** A schema 0.2 contract may declare `ci_requirements`, a short
   list of `{check, app_id}` pairs: a check-run name bound to a numeric GitHub
   App ID. The list is part of the reviewed contract, so it is covered by the
   contract hash, the mandate and the final sign-off.
2. **Gate.** For schema 0.2 **completion** only, a requirement is met when all
   of these hold on the exact published and tested head `H`:
   - every check run named exactly `check`, from app `app_id`, on `H` is
     `completed` with `success`;
   - every check suite from that app on `H` is `completed`;
   - at least one such run exists;
   - the suite and run reads are complete and below GitHub's suite window.

   There is no "latest attempt" selection. Anything else blocks completion and
   is reported.
3. **`.github/` rule.** A contract with requirements cannot complete if its
   implementation diff touches `.github/`. This is defence in depth against
   direct workflow edits, not proof that CI is independent of the change.

Commit statuses never satisfy a requirement. Schema 0.1, and 0.2 contracts
without requirements, keep their reads, outputs and decisions. `--observe-ci`
stays report-only and byte-compatible.

## Invariants

1. CI results are an observation, never proof that the evidence's checks equal
   CI's, and never a replacement for review or human sign-off.
2. Missing, partial, ambiguous or unbound data never passes a requirement.
   Ambiguity is resolved by failing closed, never by choosing one observation
   over another.
3. Schema 0.1 is unchanged. 0.2 contracts whose `ci_requirements` is absent or
   `[]` keep identical reads, decisions and output.
4. GitHub reads stay fixed `GET`s; the CLI never re-runs, re-requests or
   approves anything.

## Where requirements are declared

| Option | Verdict |
| --- | --- |
| **Task contract** (`ci_requirements` in schema 0.2) | **Chosen.** It is the reviewed artifact. Its hash binds the mandate and final sign-off, so the worker cannot weaken it, and the host and reviewer see it. |
| Host-context record | Rejected. A requirement belongs to the task, not to one issuance. |
| Repository policy (`.agent-contrib.json`) | Rejected for now. That file governs source approval; mixing in execution gates blurs authorities. |
| Live branch rulesets only | Rejected as the source of truth. Used to pre-fill and drift-check the contract, never to decide. |

```json
"ci_requirements": [
  {"check": "test", "app_id": 15368}
]
```

- 0 to 20 entries, unique pairs, no other keys.
- `check` is 1 to 200 characters. It may not contain control or format
  characters (Unicode categories Cc and Cf), and it is compared exactly
  (case-sensitive, no normalisation).
- `app_id` is a positive integer; booleans are rejected. 15368 (GitHub Actions)
  gets no special treatment: one app identity can back many workflows, and the
  check name plus review decide which one counts.
- `app_id` is mandatory. Without it, "a check named `ci` exists" would be met by
  any app with `checks:write`.
- Absent and `[]` mean "no requirements": no CI read, no `ci_gate` output, no
  blocker.
- Reviewed-contract rule: a non-empty list requires `create_draft` in
  `execution.requested_actions`. Without a pushed head there is no CI to
  observe.
- Old candidate builds reject the new property, which fails closed. Existing
  contracts without it keep their canonical hash; nothing is migrated.

## What "met" means

At completion, with the published draft already verified at `H =
evidence.git_head` (the existing exact-head rule), the CLI makes two reads, once
for all requirements.

### Read 1: suites (coverage and pending state)

```text
repos/{target}/commits/{H}/check-suites
```

The reads are counted pages, at most 10 pages of 100. Each suite must have:
- a positive integer `id`;
- `head_sha == H`;
- an `app.id`;
- a known `status`.

GitHub's commit check-runs endpoint only covers the newest 1,000 suites of a
ref (CI-04). If `total_count >= 1000`, or the read is incomplete, every
requirement is `unknown`.

### Read 2: runs

```text
repos/{target}/commits/{H}/check-runs?filter=all
```

The reads are counted pages, at most 40 pages. With fewer than 1,000 suites,
this endpoint covers every suite of the ref. Each run must have:
- a positive integer `id`;
- `head_sha == H`;
- an `app.id`;
- a `check_suite.id` that appears in read 1;
- a known `status`, and a `conclusion` consistent with that status.

A run whose suite is not in read 1 means the two reads are inconsistent, so the
result is `unknown`.

### Decision per requirement `{check, app_id}`

1. **Matching runs** are the runs whose **raw** API `name` equals `check`
   exactly, with `app.id == app_id`.
   - The raw name is a string validated for type only. It is never sanitised or
     truncated before comparison (CI-03).
   - Sanitising is for display only, in a separate field.
   - Same-name runs from other apps are ignored for satisfaction and counted as
     `other_app_runs`.
2. **App suites** are the suites from read 1 with `app.id == app_id`.
3. The requirement's state is decided in this order. The first state that
   applies wins:

| Condition | State |
| --- | --- |
| Read 1 or read 2 incomplete, malformed, inconsistent or at the suite window | `unknown` |
| Any matching run is completed with `failure`, `timed_out`, `cancelled`, `stale` or `startup_failure` | `failed` |
| Any matching run is completed with `neutral` or `skipped` | `not_met` |
| Any matching run is not `completed`, or completed with `action_required` | `pending` |
| Any app suite is not `completed` (queued, in progress, requested, waiting or pending) | `pending` |
| No matching run | `missing` |
| Otherwise: every matching run is completed with `success`, and every app suite is completed | `met` |

Only `met` for every requirement passes. Every other state is a completion
blocker that names the requirement, its state and the run or suite IDs that
caused it.

### Why no "latest attempt" selection (CI-01)

Several runs with the same name, from the same app, can be distinct current
jobs: matrix legs, or two workflows with the same job name. A higher ID does not
prove that one run is a retry of another, and `filter=latest` is defined by
completion time, not by attempt lineage. So **every** matching run must succeed.

The cost is liveness. A failed attempt that is later retried successfully at the
same head still blocks, because the CLI cannot prove the failure was superseded.
To recover, push a new commit, which means a new head, new evidence and a new
draft verification. Provider-specific attempt lineage (GitHub Actions
`run_attempt` from the workflow-runs API) could relax this later only if it
provably identifies superseded observations. It is not proposed.

### Why every app suite must be completed (CI-02)

Rerequesting a run or suite resets the suite to `queued`, while the old run can
stay `completed` + `success` until the app acts. A suite that has not emitted
its runs yet is equally invisible to read 2. So every suite of the required app
on `H` must be `completed`.

A suite's own conclusion is not required: unrelated jobs in the same app may
legitimately fail or be skipped, and only the named check is the contract.

The cost: a stuck, unrelated suite of the same app on `H` (for example a
workflow waiting for deployment approval) keeps the requirement `pending` until
it completes. This is documented.

### Further conservative choices

- **Neutral and skipped never pass**, unlike GitHub's own required checks: an
  unexecuted job proves nothing.
- **Statuses are reported, never accepted.** Commit statuses have no app
  binding.
- **Exact head only.** Runs on a merge ref, a merge-queue ref or another commit
  never count. A producer that only reports on a merge commit is unsupported and
  shows as `missing`.

  Conversely, a run on `H` does not prove which tree the job checked out.
  `pull_request` workflows check out the synthetic merge ref by default, yet
  their runs are associated with the head SHA. The output and docs say so.
- **Reads are not an atomic snapshot.** A run or suite created after the reads
  is unseen. The suite-state rule covers the known pending states that already
  exist when reading.

## Which stage it gates

**Completion only.** Implementation and draft creation happen before CI can
run on the pushed head, so gating them would deadlock.

- Gate blockers go only into `stage_blockers.completion`. They never touch the
  implementation or draft blockers, publication identity, or the generic errors
  those gates use.
- The CI reads happen before the final expiry decisions for sign-off and
  overlap dispositions, or the expiry is re-evaluated after them. That keeps
  the current rule that time-sensitive records are judged after every blocking
  read.

**`.github/` rule.** If any path in the validated implementation diff
`base_commit..git_head` is under `.github/`, completion is blocked with "CI
requirements cannot be met by a change that edits .github/". The diff counts
additions, deletions and renames (both sides), and is never inferred from
`allowed_paths` or the evidence.

- **Why:** this is defence in depth against a direct edit of a gated workflow,
  which same-repository `push` and `pull_request` runs read from the head.
- **What it does not prove:** that CI is independent of the change. An
  unchanged workflow can run `make test`, `scripts/ci.sh`, a local action under
  `actions/`, project test configuration or fixtures, all outside `.github/`.
  Remote reusable workflows can also change behind floating references. Review
  remains responsible for those.
- **Trade-off:** an opted-in contract cannot cover harmless `.github/` tasks
  either, such as issue templates or FUNDING.

Final sign-off stays a separate human record. The host should issue it after
seeing the `ci_gate` result; the CLI does not order the two.

## Forks, drafts and workflow approval

- **Forks.** The 0.2 route is same-repository only, so fork PRs are out of
  scope. Schema 0.1 cannot opt in. If a future route adopts this gate, it must
  keep the approval rule below.
- **Workflow approval.** A first-time-contributor or environment approval can
  hold a run as `action_required` or `waiting`, which is `pending`. An
  approval-required workflow can also have no check run at all yet, which is
  `missing`. Both block. The CLI never approves anything.
- **Drafts.** The completion route requires an open draft. If a repository does
  not run the required job for draft PRs, or the job is conditional and
  skipped, the requirement cannot be met. Taking the PR out of draft would
  break the existing route. The contract reviewer must check this when opting
  in.

## Output

`verify` adds `ci_gate` only when the contract declares requirements:

- `requirements`: one entry per requirement, each with:
  - `check` and `app_id`, the reviewed values;
  - `state`;
  - `runs`: the matching runs' IDs, status, conclusion and URL;
  - `blocking_suites`: the IDs of app suites that are not completed;
  - `other_app_runs`.
- `head_sha`, `suites_read`, `complete` and `errors`.
- A fixed note that a run on `H` does not prove which tree was tested.

Display names are sanitised copies; identity never uses them.

`--observe-ci` keeps its exact output. It needs a separate internal raw-record
parser so that the gate's identity fields never leak into it. The output
schema 1 (unreleased) gains the optional `ci_gate` property.

## Pre-fill and drift (report only)

These apply to newly prepared contracts only. Existing contracts gain no
fields, reads or migrations.

- `prepare --schema-version 0.2` reads `rules/branches/{base_ref}` (public
  metadata read, already used by `signatures.py`).
  - Each `required_status_checks` entry with a positive integer
    `integration_id` becomes a suggested `ci_requirements` entry. It is not
    authority until the contract is reviewed.
  - An entry without a usable `integration_id`, more than 20 candidates, or a
    failed or incomplete rules read adds an explicit review question. It never
    truncates the list or treats the read as an empty set.
- `drift` reports ruleset requirements added or removed since preparation. It
  never rewrites the contract.

## Threat model

| Threat | Handling |
| --- | --- |
| Another app posts a successful run with the required name | Bound by numeric `app_id`; other apps' runs are counted, never accepted. |
| A commit status `ci: success` | Statuses never satisfy a requirement. |
| Two distinct same-name jobs, one failing (matrix legs, two workflows) | Every matching run must succeed; there is no highest-ID selection (CI-01). |
| Rerequested run or suite whose old run still shows success | Every app suite must be `completed`; a queued suite is `pending` (CI-02). |
| A look-alike name (`test` plus a zero-width or control character, or a long name sharing a 200-character prefix) | Exact raw comparison; requirements cannot contain Cc/Cf characters; display sanitising never feeds identity (CI-03). |
| Old failing suites outside the 1,000-suite endpoint window | Suite enumeration first; a window-sized count is `unknown` (CI-04). |
| The contribution edits the gated workflow | Completion blocks on any `.github/` path in the diff. Other in-repository CI inputs remain a review duty. |
| Results for a different commit, a merge ref or a merge queue | Only `head_sha == H`; anything else is unseen, so `missing`. |
| Skipped or neutral jobs | `not_met`. |
| Workflow awaiting approval | `pending`, or `missing` if no run exists yet. |
| Truncated, moving or inconsistent reads | `unknown`. Reads are not atomic; this is stated in the output and docs. |
| Worker drops or weakens a requirement | The field is hashed and reviewed; changing it needs re-review and a new mandate. |
| A weak but valid requirement | Human review of the contract. Drift against rulesets is reported, never enforced. |
| CI tests differ from evidence tests | Documented: the gate observes CI; it does not reconcile it with evidence. |

## Compatibility

- Schema 0.1: no field, no reads, no decision change.
- Schema 0.2 with `ci_requirements` absent or `[]`: identical reads, decisions
  and output. Goldens stay byte-identical; a call-log test proves no CI read.
- With requirements, only completion can newly fail.
- `--observe-ci` output is byte-identical.
- Newly prepared 0.2 contracts may gain pre-filled suggestions and one rules
  read in `prepare`. Existing contracts are never changed.

## API cost

With requirements, at completion time:

- **Logical pages:** at most 10 suite pages plus 40 run pages. Usually it is
  1 plus 1 to 3.
- **HTTP attempts:** each request may be retried up to three times, so the worst
  case is 150 attempts.
- **Sharing:** all requirements share the same two reads.
- **Budget:** a total traversal budget stops the gate with `unknown` when it is
  exhausted. `--report-budget` counts attempts as well as logical requests.
- **Pre-fill:** `prepare` adds 1 to 2 rules pages, and `drift` reads them again.

## Slices

0. **Live read-only probe (human-run).** Record the following:
   1. the suites endpoint's shape, `app.id`, `status` values and `total_count`
      for a head with several workflows;
   2. a rerequested suite's state while its old run still shows `success`, if a
      maintainer can trigger one;
   3. how `filter=all` reports multiple attempts;
   4. `rules/branches/{branch}` readability and the `integration_id` shape.

   The gate's correctness does not depend on ID ordering or on attempt lineage.
1. **Schema and pure decision.**
   - The optional `ci_requirements` field and the reviewed-contract rules.
   - A separate raw gate parser for runs and suites, with exact raw names and
     validated IDs. `--observe-ci`'s sanitising parser stays as it is.
   - A pure `ci_gate(requirements, suites, runs, head)` that implements the
     table above.
   - A fix to `remote.counted_pages` query composition, which currently produces
     `?filter=all?per_page=...`: structured query values, with tests that
     `filter=all` and pagination are both sent.
2. **Completion gate.**
   - The two reads and the traversal budget.
   - The `.github/` rule on the validated diff.
   - The `ci_gate` output and its schema.
   - Completion-only blockers.
   - Ordering against the expiry decisions.
3. **Pre-fill and drift.**

## Test plan

- **Schema:**
  - The field is optional, and `[]` behaves exactly like an absent field.
  - These are rejected: duplicates, more than 20 entries, a blank or over-long
    `check`, Cc/Cf characters, a boolean or non-positive `app_id`, and unknown
    keys.
  - A non-empty list without `create_draft` is rejected.
- **Pure decision:** one fixture per table row, plus:
  - Two distinct same-name runs from the same app in one suite, one failed and
    one succeeded: `failed`. Also the IDs swapped, and the runs in two suites
    (CI-01).
  - A genuine retry where the earlier attempt failed and the later one
    succeeded: `failed`, documenting the liveness limit.
  - A queued app suite whose old run still shows `success`: `pending`. Also a
    queued app suite with no runs at all (CI-02).
  - Raw names: `test` against `test​`, `te\x1bst`, `Test`, ` test`, a
    non-ASCII look-alike, and a 200-character prefix plus a suffix. None
    matches a `test` or prefix requirement (CI-03).
  - The suite window: `total_count` 1000 or more gives `unknown`, independently
    of the 40-page cap fixture (CI-04).
  - A run whose suite is not in read 1: `unknown`.
  - A run from another app with the right name: counted, not accepted.
  - A run for the wrong head: ignored.
  - Results that do not depend on response order.
- **Reads:**
  - The page caps, a repeated ID, a changing `total_count`, a malformed run or
    suite, a missing `check_suite`, API errors and an exhausted budget all give
    `unknown`.
  - The query string carries both `filter=all` and the pagination parameters.
- **`.github/` rule:** a modification, an addition, a deletion and a rename out
  of `.github/workflows/ci.yml` each block. An unrelated path does not.
- **Integration (0.2):**
  - A published draft, valid sign-off and every requirement met gives
    `completion_ready`.
  - A pending, failed or `unknown` requirement gives a named completion
    blocker, while implementation and draft are unchanged.
  - Absent or `[]` requirements are identical to today, with no CI read (call
    log).
  - With an advancing clock, a sign-off that expires during the CI reads is
    still rejected.
- **Compatibility:** schema 0.1 goldens and the `--observe-ci` bytes are
  unchanged.
- **Pre-fill and drift:**
  - Entries with and without a usable `integration_id`.
  - More than 20 candidates.
  - An unreadable ruleset gives a question, not an empty set.
  - Drift reports added and removed requirements.
- **Mutants must be killed** on each of these:
  - app binding and head binding;
  - the all-matching-runs rule (not highest ID);
  - the app-suites-completed rule;
  - the suite window;
  - raw-name identity;
  - neutral/skipped rejection;
  - the `.github/` rule, including deletions and renames;
  - the empty-list read skip and the completion-only placement.

## Not proposed (YAGNI)

- Commit-status requirements.
- Accepting neutral or skipped.
- Attempt-lineage recovery for retries at the same head.
- Merge-queue or merge-ref checks.
- Workflow-file pinning by blob hash.
- Re-running, re-requesting or approving workflows.
- Gating the implementation or draft stages.
- Reconciling CI with evidence tests.
- A repository-policy default for requirements.
- Classic branch-protection reads.
