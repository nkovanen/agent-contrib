# Required CI checks for the exact head: design proposal

- Date: 2026-11-03
- Status: proposal, not implemented. Issue [#17](https://github.com/nkovanen/agent-contrib/issues/17),
  the gating half. The report-only `verify --observe-ci` already ships in the
  v0.3.0 candidate.
- Base: `efe7e68` (unreleased v0.3.0 candidate).

## Summary

Evidence is self-attested. Once the draft PR exists, GitHub can report CI
results for its exact head. These are an independent observation the worker
did not write.

This design proposes one opt-in gate:

1. **Declaration.** A schema 0.2 contract may declare `ci_requirements`, a short
   list of `{check, app_id}` pairs. Each pair is a check-run name bound to a
   numeric GitHub App ID. The list is part of the reviewed contract, so it is
   covered by the contract hash, the mandate and the final sign-off.
2. **Gate.** For schema 0.2 **completion** only, every requirement must be met
   by check runs on the exact published and tested head. Each run must come
   from that app, and the latest attempt in every matching check suite must have
   concluded `success`. Anything else blocks completion and is reported:
   pending, queued, approval-required, neutral, skipped, failed, missing or
   unreadable.
3. **Additional rule.** A contract with requirements cannot complete if its
   implementation diff edits `.github/`. A same-repository contribution could
   otherwise rewrite the very GitHub Actions workflow it is gated on.

Commit statuses are not accepted for requirements, because they carry no app
identity. Schema 0.1, and 0.2 contracts without `ci_requirements`, behave
exactly as today. `--observe-ci` stays report-only.

## Invariants

1. CI results are an observation, not proof that the evidence's checks equal
   CI's checks, and never a replacement for review or human sign-off.
2. Missing, partial, ambiguous or unbound data never passes a requirement.
3. Schema 0.1 is unchanged. 0.2 contracts without the field keep identical
   decisions, outputs and reads.
4. GitHub reads stay fixed `GET`s; the CLI never re-runs or approves workflows.

## Where requirements are declared

| Option | Verdict |
| --- | --- |
| **Task contract** (`ci_requirements` in schema 0.2) | **Chosen.** It is the reviewed artifact. Its hash binds the mandate and final sign-off, so the worker cannot weaken it, and the host and reviewer see it. |
| Host-context record | Rejected. A requirement belongs to the task, not to one issuance. It would also force re-issuing mandates whenever the requirements change. |
| Repository policy (`.agent-contrib.json`) | Rejected for now. That file governs source approval (label delegation), and mixing in execution gates blurs authorities. A maintainer-level default can come later. |
| Live branch rulesets only | Rejected as the source of truth. `rules/branches/{branch}` exposes `required_status_checks` with an optional `integration_id`, but classic branch protection is admin-only, and many repositories have neither. Rulesets are used to **pre-fill and drift-check** the contract, not to decide. |

**Schema change.** Task schema 0.2 exists only in the unreleased v0.3.0
candidate. This proposal adds an **optional** `ci_requirements` property
there:
- 0.2 contracts that lack it stay valid and unchanged;
- a 0.2 contract containing it is rejected by older candidate builds, which
  fails closed.

If the release owner treats 0.2 as frozen, the same field moves to a new
schema 0.3 instead, with no other change. This decision is needed before
Slice 1.

```json
"ci_requirements": [
  {"check": "test", "app_id": 15368}
]
```

- 0 to 20 entries. `check` is 1 to 200 characters and compared exactly
  (case-sensitive). `app_id` is a positive integer. Pairs are unique.
- `app_id` is mandatory. A requirement that "a check named `ci` exists" would
  be met by any GitHub App with `checks:write` on the repository.
- Reviewed-contract rule: if `ci_requirements` is non-empty,
  `execution.requested_actions` must include `create_draft`. Without a pushed
  head there is no CI to observe.

## What "passed" means

For the completion stage, with the published draft already verified at
`evidence.git_head` (the existing exact-head rule), read:

`repos/{target}/commits/{git_head}/check-runs?filter=all`

This uses the existing counted-page reader (`remote.counted_pages`): stable
`total_count`, unique IDs, at most 40 pages, and fail-closed on any malformed
item. `filter=all` is used so that re-runs are visible rather than
pre-collapsed by GitHub.

For each requirement:

1. Select runs with `name == check`, `app.id == app_id` and
   `head_sha == git_head`.
   - Runs from other apps with the same name are ignored, but counted in the
     output as `other_app_runs`.
   - Runs for other heads are ignored.
2. Group them by `check_suite.id`. In each suite take the run with the highest
   `id` as its latest attempt (Slice 0 confirms that re-runs get higher IDs).
3. The requirement is **met** only if at least one suite exists and the latest
   attempt in **every** suite is `status: completed` with
   `conclusion: success`.

Conservative choices, each documented:

- **Neutral and skipped do not pass.** GitHub's own required checks treat
  `neutral` and `skipped` as passing; this gate does not, because an
  unexecuted job proves nothing.
- **Several suites must all succeed.** For example, `push` and
  `pull_request` workflows produce same-name runs in separate suites. A
  newer failing suite is never hidden by an older successful one.
- **Statuses are reported, never accepted.** Commit statuses (`/status`) have
  no app binding.

| Observed latest attempt | Result |
| --- | --- |
| `completed` + `success` (in every suite) | met |
| `queued`, `in_progress`, `waiting`, `requested`, `pending` | `pending` |
| `completed` + `action_required` (for example workflow approval) | `pending` |
| `completed` + `neutral` / `skipped` | `not_met` |
| `completed` + `failure` / `timed_out` / `cancelled` / `stale` / `startup_failure` | `failed` |
| no matching run | `missing` |
| read failed, incomplete or malformed | `unknown` |

Only `met` for every requirement passes. Any other value is a completion
blocker naming the requirement and its state.

## Which stage it gates

**Completion only.** Implementation and draft creation happen before CI can
run on the pushed head, so gating them would deadlock. The existing gates
already require a fully verified exact-head published draft at
`evidence.git_head` before completion. The CI gate adds:

- the `.github/` rule: if any implementation path (`base_commit..git_head`)
  is under `.github/`, completion is blocked with "CI requirements cannot be
  met by a change that edits .github/". GitHub runs same-repository
  `push` and `pull_request` workflows from the head commit, so such an edit
  could rewrite the gated check. Other CI systems that read in-repository
  configuration are a reviewer responsibility, and the docs say so;
- the per-requirement results above.

Final sign-off stays a separate human record. The host should issue it after
seeing the `ci_gate` result; the CLI does not order the two.

## Forks and workflow approval

The 0.2 route is same-repository only, so fork PRs are out of scope. Even in
the same repository, first-time-contributor or environment approval can hold a
run as `action_required` or `waiting`, which is `pending` and never passes. The
CLI never approves or re-runs anything. If a 0.1 fork route or #22 ever adopts
this gate, it must keep that rule.

## Output

`verify` adds `ci_gate` only when the contract declares requirements:

- `requirements`: one entry per requirement, with `check`, `app_id`, `state`,
  the latest run IDs/URLs per suite and `other_app_runs`;
- `head_sha` and `complete`;
- `errors`.

Its blockers appear in `stage_blockers.completion`. Contracts without
requirements produce identical output. Output schema 1 is also unreleased: the
optional property is added there, under the same release-owner decision as the
task schema.

`--observe-ci` keeps its report-only behaviour and output.

## Pre-fill and drift (report only)

- `prepare --schema-version 0.2` reads `rules/branches/{base_ref}`, which
  `signatures.py` already reads.
  - Each `required_status_checks` entry with an integer `integration_id`
    becomes a `ci_requirements` entry.
  - Entries without an `integration_id` add a review question instead of a
    requirement.
  - A failed or incomplete rules read adds a question; it is never treated as
    an empty requirement set.
- `drift` reports ruleset requirements added or removed since preparation.
  It never rewrites the contract.

## Threat model

| Threat | Handling |
| --- | --- |
| Another app posts a successful run with the required name | Bound by numeric `app_id`; other apps' runs are ignored and counted. |
| Someone with write access posts a commit status `ci: success` | Statuses never satisfy a requirement. |
| The contribution edits the gated workflow so it trivially passes | Completion blocks if the implementation diff touches `.github/`. Other in-repository CI configuration is documented as a review duty. |
| Results for a different commit | Only `head_sha == evidence.git_head`, which is also the verified draft head. |
| A flaky check is re-run and an older attempt succeeded | The latest attempt per suite decides; an in-progress re-run is `pending`. |
| A stale success hides a newer failing suite | Every suite's latest attempt must succeed. |
| Skipped or neutral jobs (path filters, `if:` conditions) | `not_met`; they prove nothing ran. |
| Workflow awaiting approval | `pending`. |
| Pagination truncated or moving | The counted reader yields `unknown`. Reads are not an atomic snapshot: a run created after the read is unseen. Stated in output and docs. |
| Worker drops or weakens a requirement | The field is in the hashed, reviewed contract; changing it needs re-review and a new mandate. |
| A weak but valid requirement (a trivial check) | Human review of the contract. Drift against live rulesets is reported, never enforced. |
| Repository later changes rulesets | Reported by `drift`; the contract's own requirements still apply. |
| CI tests differ from evidence tests | Documented: the gate observes CI; it does not reconcile it with evidence. |

## Compatibility

- Schema 0.1: no field, no reads, no decision change.
- Schema 0.2 without `ci_requirements`: identical reads, decisions and
  output. Goldens must stay byte-identical.
- With requirements, only completion can newly fail.
  `implementation_ready`, `draft_create_ready` and their blockers are
  unchanged.
- The `--observe-ci` output stays the same.

## API cost

With requirements only: the check-run pages for the head at completion time,
usually 1 to 3 at 100 per page. With `prepare` pre-fill: 1 to 2 rules pages.
`drift`: the same rules read again.

## Slices

0. **Live read-only probe (human-run).** Confirm:
   1. that a re-run gets a higher check-run `id` in the same `check_suite`;
   2. that `filter=all` returns every attempt;
   3. the `check_suite.id` and `app.id` shapes;
   4. that `rules/branches/{branch}` is readable without push access, and its
      `integration_id` shape;
   5. which workflow file same-repository `pull_request` runs use.
1. **Schema and pure decision.** The optional `ci_requirements` field (or
   schema 0.3, per the decision above), reviewed-contract rules, and a pure
   `ci_gate(requirements, runs, head)` function. Check-run parsing gains
   `check_suite.id`. No lifecycle wiring yet.
2. **Completion gate.** The `filter=all` read at completion, the `.github/`
   rule, `ci_gate` output and schema, and completion blockers.
3. **Pre-fill and drift.** `prepare` from rulesets, and the `drift` report.

## Test plan

- **Schema:**
  - The field is optional; existing 0.2 fixtures and goldens are unchanged.
  - These are rejected: duplicates, more than 20 entries, a blank `check`,
    `app_id` that is not a positive integer, and unknown keys.
  - Requirements without a `create_draft` action are rejected.
- **Pure decision.** One fixture per table row:
  - success in a single suite;
  - success in one suite and failure in another;
  - a re-run attempt that is in progress, and one that failed after an earlier
    success;
  - `action_required`, `neutral`, `skipped`, and each failing conclusion;
  - a run from the right name but another app;
  - a run for the wrong head;
  - no runs at all;
  - same-ID ordering independent of response order.
- **Reads:** a 40-page cap, a repeated ID, a changing `total_count`, a
  malformed run, a missing `check_suite`, and API errors all give `unknown`,
  and completion stays blocked.
- **`.github/` rule:** an implementation touching `.github/workflows/ci.yml`
  blocks completion even when every run succeeds. An unrelated path does not.
- **Integration (0.2):**
  - published draft, valid sign-off and requirements met → `completion_ready`;
  - the same with one requirement `pending` → not ready, with a named blocker;
  - without requirements → identical to today, and no check-run read (call
    log).
- **Compatibility:** schema 0.1 goldens and `--observe-ci` output are
  unchanged.
- **Pre-fill and drift:** ruleset entries with and without `integration_id`;
  an unreadable ruleset gives a question, not an empty set; drift reports
  added and removed requirements.
- **Mutants** must be killed on the app-ID binding, head binding, latest-per-
  suite selection, all-suites rule, neutral/skipped rejection, the `.github/`
  rule and the no-requirements read skip.

## Not proposed (YAGNI)

- Commit-status requirements.
- Accepting neutral or skipped.
- Workflow-file pinning by blob hash.
- Re-running or approving workflows.
- Gating implementation or draft stages.
- Reconciling CI with evidence tests.
- A repository-policy default for requirements.
- Classic branch-protection reads (admin-only).
